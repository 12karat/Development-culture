# NETWORKING_NOTES.md

## Четыре случая адресации — и почему они разные

---

### 1. Локальный запуск: `127.0.0.1` работает

```bash
# Терминал 1
uvicorn product_service.main:app --port 8001

# Терминал 2
uvicorn order_service.main:app --port 8002 \
  --env PRODUCT_SERVICE_URL=http://127.0.0.1:8001
```

Оба процесса запущены **на хостовой машине**. `127.0.0.1` — это loopback-интерфейс хоста. Когда order-service делает запрос на `http://127.0.0.1:8001`, операционная система видит, что адрес назначения — сам хост, и направляет пакет прямо к слушающему сокету product-service. Никакой сети нет — всё происходит внутри одной ОС.

---

### 2. Запуск в контейнерах с `127.0.0.1` — **не работает**

```bash
docker run -e PRODUCT_SERVICE_URL=http://127.0.0.1:8001 order-system/order-service
```

Внутри контейнера `127.0.0.1` означает **сам контейнер**, а не хостовую машину. У каждого контейнера — собственный сетевой стек. Порт 8001 внутри контейнера order-service никто не слушает, поэтому запрос упадёт с ошибкой `Connection refused`.

Даже если product-service опубликован наружу как `-p 8001:8000`, это значит, что он доступен с хоста по адресу `127.0.0.1:8001` — но **не** изнутри другого контейнера.

**Ошибка в логах order-service:**
```
httpx.ConnectError: [Errno 111] Connection refused
```

---

### 3. Контейнеры в одной сети, общение по имени сервиса — **правильный способ**

```bash
docker network create order-net

docker run --name product-service --network order-net \
  order-system/product-service

docker run --name order-service --network order-net \
  -e PRODUCT_SERVICE_URL=http://product-service:8000 \
  order-system/order-service
```

Docker встроенный DNS резолвит имя контейнера (`product-service`) в его внутренний IP-адрес внутри сети `order-net`. Никакого `localhost`, никаких хостовых портов — контейнеры общаются напрямую через виртуальную сеть.

В `docker-compose.yml` то же самое происходит автоматически: Compose создаёт общую сеть и регистрирует каждый сервис по его имени из файла.

**Важно:** внутренний порт — это `8000` (порт внутри контейнера), а не `8001` или `8003` (порты, опубликованные на хосте). Публикация порта на хост и доступность внутри Docker-сети — это **две независимые вещи**.

---

### 4. Из контейнера к хосту: `host.docker.internal` (необязательно)

Иногда контейнеру нужно обратиться к сервису, запущенному непосредственно на хостовой машине (например, к локальной базе данных во время разработки):

```bash
docker run -e DB_URL=postgresql://host.docker.internal:5432/mydb myapp
```

`host.docker.internal` — специальное DNS-имя, которое Docker резолвит в IP-адрес хоста. На macOS и Windows оно работает из коробки. На Linux нужно явно добавить флаг `--add-host=host.docker.internal:host-gateway`.

**Когда использовать:** только во время разработки, когда какой-то инструмент (база данных, сервис мониторинга) ещё не контейнеризован. В production все зависимости должны быть в сети контейнеров.

## Диагностические случаи

### Ошибка 1: неправильный URL внутри Compose

```yaml
# НЕПРАВИЛЬНО — внутри контейнера это сам order-service, не хост
environment:
  PRODUCT_SERVICE_URL: http://127.0.0.1:8001
```

**Что происходит:** order-service пытается подключиться к самому себе на порт 8001. Там ничего нет. `Connection refused`.

**Правильно:**
```yaml
environment:
  PRODUCT_SERVICE_URL: http://product-service:8000
```

---

### Ошибка 2: отсутствует переменная окружения

```yaml
environment:
  PRODUCT_SERVICE_URL: http://product-service:8000
  # DISCOUNT_SERVICE_URL забыли
```

**Что происходит:** при старте order-service вызывается `startup_check()`, который обнаруживает отсутствующую переменную и бросает `RuntimeError`:

```
RuntimeError: Missing required environment variables: DISCOUNT_SERVICE_URL.
```

Контейнер завершается с ненулевым кодом возврата. Это намеренное поведение — лучше упасть сразу с понятной ошибкой, чем падать в runtime при первом запросе.

---

### Ошибка 3: смена опубликованного порта хоста — внутренние URL менять не нужно

```yaml
# Было: - "8001:8000"
# Стало:
ports:
  - "9001:8000"
```

**Что происходит:** с хоста теперь нужно использовать `http://127.0.0.1:9001`. Но order-service обращается к product-service **внутри Docker-сети**, а не через хост. Поэтому `PRODUCT_SERVICE_URL=http://product-service:8000` остаётся верным без изменений.

Это ключевое разграничение: **порт хоста** — для людей и внешних клиентов; **внутренний порт контейнера** — для межсервисного взаимодействия.

---

## Главный вывод

Каждый раз, когда пишешь URL для HTTP-запроса, нужно задать вопрос:

> **Где выполняется этот код?**

| Где выполняется код | `127.0.0.1` означает |
|---|---|
| На хостовой машине | Хост |
| Внутри контейнера | Этот контейнер |
| Нужно попасть в другой контейнер | Имя сервиса в общей Docker-сети |
| Нужно попасть на хост из контейнера | `host.docker.internal` |

`localhost` — не универсальный адрес. Это просто «я сам», а кто такой «я» — зависит от контекста выполнения.
